# decision-32: colors.json をスナップショット正とし build-colors を差分追加モードにする

## Context

`data/colors.json` は TASK-119（900 年スナップショット廃止）以降
`build-colors` が再実行されず、900 年由来の 34 キーとそれを前提にした
線形プロービングの割当状態が凍結していた。パレットは 288 スロット中 287
使用済みで、全量再生成するとプロービング連鎖のずれにより**新規追加と無関係に
既存 92 キーが変色**する（Issue #172 実装時と #193 で実測）。TASK-124 と
Issue #172 は「追加限定方式」（既存色のパレット逆引き + 新キーのみ決定的
割当）を手動で行い回避したが、build-colors 本体の出力と乖離し、再生成
可能性が失われていた。

## Decision

**colors.json をスナップショット正（ソースオブトゥルース）とし、
`build-colors` を差分追加モードに変更する。**

本 ADR は [decision-5](0005-deterministic-color-probing.md) の色割当方式を
維持しつつ、その全キー一意保証と再生成方式を一部追補する。

- 既存キーの色は無条件でバイト単位保持する。
- 新キーのみ「fnv1a 自然スロット + 線形プロービング + **同年非衝突制約**
  （同じ年の地図に同時に現れる色との衝突のみ回避。別年との色再利用は許容）」
  で決定的に追加する。属領キーは宗主の実表示色のパレット逆引きから明度
  シフトで派生する（Issue #172 方式の正式化）。
- decision-5 の「全キー一意色」保証は「同年内一意」へ緩和する（パレット
  飽和下の構造的帰結）。
- `--check` でドリフト検出（生成出力と実ファイルの乖離があれば exit 1・
  非破壊）。900 年由来の stale キー 34 件は既定で保持し、`--prune` でのみ
  除去（どの feature からも参照されず、クライアントは未登録キーをデフォルト
  色で縮退させる契約のため削除しても安全であることを実測済み）。
- colors.json が存在しない場合（bootstrap）のみ従来の全量生成を行う。

却下案: **一度だけ全量再生成してリセットする** — 全年代で 92 キー以上が
一斉に変色し、ユーザーの受容確認が必要。追加限定方式に運用実績があり、
見た目不変を保てる本方式が決定的かつ低リスク。

## Consequences

- `deno task build-colors` が再び安全に実行可能（新キーが無ければ diff
  ゼロ）。`--check` をドリフト検出として CI や finalization に組み込める。
- 色割当は path-dependent（スナップショットの履歴に依存）になる。
  colors.json は生成物ではなく**管理対象の状態**として扱う。
- 今後のキー追加（新オーバーレイ・base 是正）は build-colors の通常実行で
  済み、TASK-124 / #172 のような手動割当は不要になる。
