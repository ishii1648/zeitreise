# 調査レポート（docs/research/）

タスクの判断根拠になった**一次調査**の記録を置くディレクトリ。「なぜその方針に
したか」を後から検証できるよう、調査の対象・方法・実測値・結論を git 管理下に
残す。運用ルール（出力先の使い分け）はプロジェクト `CLAUDE.md`
の「調査ドキュメントの出力先」節と `docs/development-style.md` 2.2 章を参照。

**なぜ git 管理下に置くか:** 従来はグローバル設定に従って `.outputs/claude/`
（git 管理外）へ出力していたが、worktree の後始末とともに消えるため、コミット
済みの docs が消失した成果物を参照する状態になった（Issue #204）。判断根拠と
して参照されるレポートはリポジトリと寿命を揃える。

## 1. 置くもの / 置かないもの

**置く（`docs/research/` にコミットする）:**

- 方針・採否の判断根拠になった一次調査（データソースの実在性・品質調査、
  代替案の比較、実測に基づく現状分析）
- 後続タスクの起票根拠として本文から引用される調査（件数・比率・一覧など、
  再実行しないと再現できない実測値を含むもの）
- 手作業の観測記録（ヘッドレス CDP の実測、上流データの目視確認結果など）で、
  結論が他の docs から参照されるもの

**置かない（`.outputs/claude/` のままでよい）:**

- スクリプト 1 コマンドで作り直せる中間生成物（`deno task audit-rivers` /
  `deno task audit-attribution` の出力、ビルド診断の JSON など）
- 検証スクリーンショット・ダウンロードキャッシュ・巨大なダンプ（数百 KB 超の
  生データや全件リスト）
- 作業中のメモ・試行錯誤のログ

判断に迷う場合の基準は「**他の docs・Issue・ADR がこの成果物を根拠として指す
可能性があるか**」。指すなら `docs/research/`、指さないなら `.outputs/claude/`。
中間生成物を docs から参照するときは、パスではなく**生成コマンドを併記**する
（例: 「`deno task audit-attribution` が生成する
`.outputs/claude/task-103/attribution-audit.md`（git 管理外）」）。

## 2. 他ディレクトリとの棲み分け

| ディレクトリ           | 置くもの                                                   | 粒度・寿命                                             |
| ---------------------- | ---------------------------------------------------------- | ------------------------------------------------------ |
| `docs/research/`       | **判断の根拠**になった調査の記録（本ディレクトリ）         | 調査時点のスナップショット。原則として後から更新しない |
| `docs/adr/`            | **決定**の記録（Context / Decision / Consequences）        | 決定単位。supersede されるまで有効                     |
| `docs/data-inventory/` | **データの台帳**（何が入っているか・既知の欠落・監査結果） | データが変わるたびに更新する生きたドキュメント         |
| `.outputs/claude/`     | 再生成可能な中間生成物                                     | git 管理外。いつ消えてもよいもの                       |

同じ調査から ADR が生まれる場合、**根拠は `docs/research/`・決定は `docs/adr/`**
に分けて書き、ADR の Context
から調査レポートを参照する（本文の二重管理をしない。 `docs/development-style.md`
2.1 章の「コンテキストコミットとの棲み分け」と同じ
考え方）。調査の結論がデータの性質そのもの（欠落・限界・監査結果）である場合は、
台帳側（`docs/data-inventory/`）に本文を置き、`docs/research/`
には手順と実測値を 残す。

## 3. 命名規約

- ファイル名は `issue-<N>-<slug>.md`（例:
  `issue-204-research-output-location.md`）。`<N>` は調査の契機になったタスク
  Issue 番号、`<slug>` は英語ケバブケース。Issue 番号を頭に置くのは、
  `docs/adr/` が `00NN-<slug>.md` で番号先頭・時系列順に並ぶ流儀に揃えるため。
- 契機の Issue が無い調査（着手前の探索・ユーザー報告直後の一次観測など）は
  `<YYYY-MM-DD>-<slug>.md`（例: `2026-08-01-tile-cache-survey.md`）とする。
  後から Issue を起票してもファイル名は変えない（リンク切れを作らない）。
- 出力が複数ファイルになる場合はディレクトリを切り、同じ規約の名前を付けて
  `README.md` を入り口にする（例: `issue-204-…/README.md`）。
- 冒頭は H1 タイトル（日本語で「何を調べたか」まで含める）+ メタ情報の箇条書き
  で始める（`docs/data-inventory/base-attribution-audit.md` の流儀に合わせる）:

  ```md
  # <調査対象> の調査（Issue #204）

  - 調査日: 2026-08-01
  - 契機: Issue #204（本文の該当箇所）
  - 使用スクリプト: `scripts/foo.ts`（`deno task foo` で再実行）
  - 結論の反映先: `docs/development-style.md` 4.2 章 / `docs/adr/0008-…md`
  ```

- 追加したら §4 の一覧に 1 行足す。

## 5. 失われた調査レポート（復元不可）

Issue #204 の時点で、コミット済みの docs が参照していた `.outputs/claude/`
配下の 一次調査レポートは**すべて消失している**（`.outputs/`
自体が存在しない）。内容は 残っていないため復元・再現はしない。参照元の docs
には注記を入れ、**結論がどこに 残っているか**を指すようにした。
